## ALTO

**1. The HTTP↔MCP correlation does not work under the mounted `/mcp`; it logs a stale id and hides the real one.**
`/Users/efra/claude/code/arb-mcp/src/arb_mcp/infra/audit.py:87-95`, `/Users/efra/claude/code/arb-mcp/src/arb_mcp/infra/http/app.py:97-98,120`, `/Users/efra/claude/code/arb-mcp/docs/AUTH.md:102-104`.
`tool_call` gives precedence to an already-bound `request_id`. In the SDK's stateful streamable HTTP (`.venv/.../mcp/server/streamable_http_manager.py:248-353`), the session's server task is created with `self._task_group.start(run_server)` *inside the first HTTP request of the session* (the `initialize` POST). asyncio copies the caller's context at task creation, so that task carries the guard's `rid` for `initialize` forever; every later `tools/call` on that session runs in that task (or its children), sees `bound is not None`, and logs the **initialize request's id** — never the id the guard minted/echoed for the current POST, and `ctx.request_id` is ignored. The HTTP line and the tool line for the same call therefore carry two different ids, which is the opposite of what commit `f50bfab`, the `tool_call` docstring, and AUTH.md claim. My spec asserted this inheritance; the assertion was wrong and was implemented without a transport-level test. `tests/test_stdio_tools.py:976-993` sets the ContextVar by hand and thus proves the mechanism, not the behaviour.
Fix: drop precedence rule 1. In the guard set `request.state.request_id = rid` (`scope["state"]` is shared with the mount); in `tool_call` read it via `getattr` chain `ctx.request_context.request.state.request_id` (`None` on stdio), then `ctx.request_id`, then fresh. Add the integration test my spec's 2c described (`streamable_http_client` over `httpx.ASGITransport`) asserting the tool line's `request_id` equals the POST's `X-Request-ID`; until it exists, remove the claim from AUTH.md:102-104 and the `audit.py` docstrings.
