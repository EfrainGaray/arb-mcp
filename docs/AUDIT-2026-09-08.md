# Consistency audit — 2026-09-08

Scope: the whole arb-mcp repository against (a) the lab engine it was vendored from
(`~/lab/2026-08-20-dsl-arquitectura/spec`), (b) its own docs and README, (c) the
project memory and the internal page published at `efraingaray.com/interno/arb-mcp`,
and (d) the design rule adopted today: **the model carries topological and ordinal
facts only, never metric ones**.

Gates at the time of the audit: `pytest` 48 passed · `ruff check src/ tests/` clean ·
`mypy --strict` clean · no upward imports between `domain/`, `application/`, `infra/`
· no secrets versioned. The code is healthy; the inconsistencies are between copies,
between docs and code, and between the code and the rule.

Severity: **high** = two sources of truth disagree on something a user relies on;
**medium** = a promise the code does not keep; **low** = hygiene.

---

## H1 · The vendored engine has drifted from the lab (high)

`src/arb_mcp/domain/_engine/` is a copy of the lab engine. The lab moved today and
the copy did not:

| file | status |
|---|---|
| `schema/architecture.schema.json` | **629 lines differ** — lab has `$defs/layout`, `$defs/placement`, `view.layout`; the copy has none |
| `grammar/architecture.ebnf` | **33 lines differ** — lab has `layout … { id at rank order }`; the copy does not |
| `inspections.py`, `implied.py`, `from_structurizr.py`, `grammar.lark` | identical |
| `convert.py` | 1 line: only the grammar path (`with_name` vs `parent / "grammar"`) — harmless |

Two consequences. The MCP cannot validate a model that carries the geometry layer
(`validate_model` would reject `view.layout` as an unknown property). And the copy
still carries the metric contamination removed from the lab today — see H2.

**Fix:** re-vendor from the lab once the layout layer is stable, in a single
`chore(domain): re-vendor engine` commit, and add a test that diffs the vendored
schema against a pinned digest so drift is caught at `pytest` time instead of at
audit time.

## H2 · `style` in the metamodel violates the ordinal-only rule (high)

`_engine/schema/architecture.schema.json` → `$defs/nodeType.properties.style` and
`$defs/relationType.properties.style`, with `shape`, `color`, `icon`, `line`. Colour
and shape are how one tool paints the model, not what the architecture is: change a
box from blue to green and the architecture did not change. The lab removed `style`
today together with the `size` that had been added by mistake; the vendored copy
still has it.

**Fix:** comes with H1. Presentation attributes move to a render profile
(`examples/c4.render.json` in the lab) that the model never references.

## H3 · Pixels hard-coded in `domain/drawio.py` (high)

`domain/` is the framework-free core, and `drawio.py` lives there with literal
geometry: `_c4_vertex(n, style, 40, y, 210, 110)` (lines 241, 289, 336),
`_vertex(sid, …, 200, 40, 320, …)` (262, 304), `pageWidth="850"` (180). These are
metric facts in the domain layer.

They are also **the wrong numbers**: drawio's own C4 palette (`Sidebar-C4.js`) is
240×120 for system/container/component and 200×180 for a person, both
`resizable=0`. The exporter emits 210×110 and 320-wide boundaries. The file opens,
but the shapes are not drawio's shapes, and the docstring's claim *"nothing is
invented"* holds for the style strings and not for the sizes.

**Fix:** `drawio.py` stays an exporter but reads sizes and gaps from a render
profile passed in by `application/convert_model.py`; the domain keeps no unit.
Take the 240×120 / 200×180 / gaps from the lab's `c4.render.json`.

## H4 · Two drawio exporters, three sizes for the same box (high)

- `arb-mcp/domain/drawio.py` — C4 views split per level (C1 / C2 per system / C3
  per container), ad-hoc column placement, 210×110.
- lab `tools/to_drawio.py` — one view, placement from `rank`/`order`, geometry
  **relative to the parent cell**, 240×120 from the profile, verified by opening the
  file in drawio (which is how the boundary-label bug was found).

Neither knows about the other. The arb-mcp exporter has the right *product* shape
(separate C4 levels, which the bank asked for); the lab exporter has the right
*model* shape (cells, not pixels; parent-relative geometry). They must merge into
one: per-level views driven by `rank`/`order`.

## H5 · An undeclared type passed the merge gate (high — fixed the same day)

Found while writing the HTTP adapter's tests, not by reading: `build_model_tool`
with a node typed `"nope"` returned `may_merge: true`, and the engine minted a rule
named `model.nope.description` from the bogus type. Nothing checked
`node.type ∈ spec.nodeTypes` or `relation.type ∈ spec.relationTypes`. The README's
claim *"the fixed spec is injected so the agent cannot invent types"* held only for
the spec being present, not enforced.

**Fixed:** `domain/linter.py` adds `model.type.undeclared` and
`model.relation.type.undeclared`, both `ERROR`, in the audited facade. Regression
tests in `tests/test_validate.py` (three) and `tests/test_http.py` (one). Agatha's
verdict is unchanged: it only uses declared types.

**Still open in the same family:** `contains` is not enforced either — a
`component` nested directly in a `person` is accepted. Same fix shape; not done here
to keep the change surgical.

## M1 · README says four tools; there are five (medium)

## M2 · `docs/API.md` does not document `check_catalog` (medium)

Zero occurrences. Root cause is `docs/gen_api.py:35`, which hard-codes the tool
list `["describe_contract", "build_model_tool", "validate_model", "convert_model"]`
instead of iterating `list_tools()` (which it already calls on line 33). The README
tells the reader to regenerate API.md; regenerating will not add the missing tool.

**Fix:** iterate the live tool list; regenerate.

## M3 · The fixed spec cannot express decisions or deployment (medium)

`application/build_model.py:21` injects `domain/specs/c4.json`, which declares
exactly four types: `person`, `softwareSystem`, `container`, `component`. The lab
spec (`examples/c4.spec.json`) declares six — adds `deploymentNode` and
`decision` — plus `relationTypes` (`uses`, `affects`, `supersedes`) and
`requires: ["technology"]` on `container`.

This contradicts META-MODEL decision 3 (*"A decision is a node, not an annex"*)
and Épica 1, whose repository is *DSL + ADRs*. Through `build_model_tool` an ADR
cannot exist. Deployment only works because `tests/fixtures/despliegue.json`
carries its **own** inline spec and goes through `validate_model(source)`, not
through the assembly tool — so the deployment example on the public page is not
reachable by the flow the page describes.

**Fix:** align `domain/specs/c4.json` with the lab spec (six types, relation
types, `requires`), and make `build_model` accept an optional spec id
(`c4`, `c4+deployment`, …) instead of one hard-wired file.

## M4 · Memory and page describe tools that do not exist (medium)

`project_arb_mcp` opens with *validate, convert, **query**, **generate (LLM)*** and
ports `JiraPort`, `LlmPort`, `DrawioPort`, adapters `infra/jira`, `infra/llm`.
`pyproject.toml:4` still says *"validation, conversion and **query**"*. The code:
no LLM at all (`README:26` — *"This MCP has no LLM and calls none"*, Kiro does the
thinking), no `query`, one port (`CatalogPort`). The later sections of the memory
record the change; the header does not. Anyone reading the top of the memory or the
package description gets the old design.

**Fix:** rewrite the memory header; change the package description to
*"deterministic C4/DSL validation, conversion and catalog reconciliation"*.

## M5 · `convert_model` accepts a target it does not advertise, and lacks one it implies (medium)

`application/convert_model.py:15` — `FORMATS = ("drawio", "structurizr")`, yet line
30 handles `"arch"`. Mermaid — named on the public page as a notation the canonical
model exports to — has no branch. `describe_contract` therefore tells a client two
formats, the code accepts three, the page promises four.

**Fix:** add `"arch"` to `FORMATS` (it works); add a Mermaid exporter or remove the
claim from the page.

## M6 · Which representation is canonical is stated two ways (medium)

The page and the memory: *"the schema rules; the text is a surface"* — the JSON is
canonical, `.arch` is one exporter among several, not on the critical path. The lab
META-MODEL and its EBNF: the DSL is *"the canonical surface"* and most tooling is
built around the text. Both can be true only if stated as one sentence: **the
schema is normative and the JSON is the interchange form; `.arch` is the authoring
surface for humans, with round-trip guaranteed**. Today each document says half.

**Fix:** put that sentence verbatim in META-MODEL.md, README.md and the page.

## M7 · A finding has no `subject` field (medium)

`domain/findings.py` — `Finding(severity, rule, message)`, and the docstring says
*"the subject is addressable"*. It is not: the subject lives inside the English
`message` string. The memory and the public page describe findings as
*(rule, severity, subject)*, and Épica 2's dashboard — compliance per team, top
ten rules, tech not in the catalog — needs to group by subject, which today means
parsing prose.

**Fix:** add `subject: str` (the element or relation id) to `Finding` and to
`to_dict()`; keep `message` as is. The ported engine already knows the subject when
it formats the message.

## Addendum · LeanIX diagrams are drawio (from the review discussion)

LeanIX's diagram editor is diagrams.net embedded and stores drawio XML. This
collapses two of the gaps the normalisation answer lists — *LeanIX manual →
canonical* and *drawio manual → canonical* — into **one importer**: drawio XML →
canonical model. drawio is already parseable here (`check_drawio` in the lab reads
its cells), and C4 cells carry typed `<object c4Type=…>` metadata. What must be
confirmed against a real LeanIX export is which metadata it stamps on each cell; if
the fact-sheet id is there, catalog identity comes for free at import time and
`check_catalog` becomes a consistency check instead of a lookup. This is the highest
value item outside this repo's current scope.

## What is consistent, and worth keeping that way

- Layering is clean: no `domain → application/infra` and no `application → infra`
  import. Domain imports only stdlib.
- The blocking rule is enforced in one place: `findings.Severity.blocking` is
  `self is Severity.ERROR`; nothing probabilistic reaches it.
- Input detection (`domain/loading.py`) handles JSON and Structurizr DSL (the `.arch` text language and its lark grammar were removed on 2026-09-09: the canonical model is the JSON, and the text authoring surface belongs to the DSL project, not to this deliverable)
  from one entry point, anchored at the start of the text so a stray `workspace`
  in a description cannot hijack it.
- Format-equivalence with the official Structurizr CLI still holds after every
  change made today, regenerated from scratch: elements 16=16, relations 20=20,
  views 3=3.

## Addendum 2026-09-09 — H1/H2 closed

The vendored `_engine/` is gone. `inspections`, `implied` and the Structurizr
parser were rewritten over the typed `Model` and live in `domain/` under the

16=16 / 20=20 / 3=3 measurement against the official CLI forward. H2 (style in
the metamodel) closes with it: `NodeType`/`RelationType` carry no style field.
